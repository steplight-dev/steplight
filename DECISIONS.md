# Decisions

Choices made where the spec was ambiguous. Simplest reasonable option wins.

1. **Repo root = this folder.** The `steplight/` folder in the spec is the repo root itself.
2. **Build tool for Node packages = plain `tsc`** (NodeNext modules, `.js` import suffixes). No bundler needed for core/sdk/cli.
3. **Core subpath exports.** `@steplight/core` (pure, browser-safe), `@steplight/core/node` (fs-based run storage), `@steplight/core/otel` (OpenTelemetry mapping). Keeps the extension/viewer bundles free of `fs` and OTel.
4. **Vite 5 + Vitest 2** so the viewer/extension share one Vite major with the test runner.
5. **Tailwind v4** via `@tailwindcss/vite` (no PostCSS config file).
6. **LICENSE** text copied verbatim from the Apache-2.0 license shipped with the `typescript` package.
7. **sensitiveOutbound email severity.** Spec says emails → critical. An email sent back to the *same site* as the page (normal login/checkout) is downgraded to `low` to honour "precision over recall"; emails to a different site, and all card/key/JWT hits, stay `critical`.
8. **crossDomainData** matches body values (≥5 chars, non-generic) against text of earlier pages that belong to a *different* site than the destination. Local ports count as distinct sites.
9. **Redaction regexes are length-bounded** (found a quadratic blow-up on 300 KB text with the unbounded email regex). Bodies/snapshots are truncated *before* redaction; a secret split at the cut point can leave a short fragment.
10. **run.json holds metadata only**; steps live in `steps.jsonl` and are merged by `readRun`.
11. **Hidden-instruction `send … to`** pattern requires an explicit target (email, URL, "the server"…) so "send us feedback to improve" is not an instruction.
12. **Fixtures arrived in Phase 3**, not 4, because the SDK acceptance test needs them; Phase 4 added the demo agent.
13. **OTel export is opt-in for the SDK** (`otel: true` or `OTEL_EXPORTER_OTLP_ENDPOINT` set) so `run.end()` never waits on a missing collector. `steplight export --otlp` always tries.
14. **Percent-decoding before matching.** Form bodies are URL-encoded (`a%40b.co`); matchers and redaction decode first. This found a real leak during integration testing.
15. **Evidence masking is kind-aware** (email → domain only, card → last 4, keys → 4-char prefix) after a test showed the generic head/tail mask exposed part of an email.
16. **Extension builds each entry as its own IIFE** via the Vite JS API (`scripts/build.mjs`), because content scripts cannot use ES-module imports/shared chunks and the spec forbids CRXJS.
17. **Extension permissions:** `activeTab`, `storage`, `scripting`, host `localhost:4777`; `<all_urls>` is *optional* and requested when the user presses Start. Without it only the current page is recorded.
18. **Extension e2e uses a patched manifest copy** (adds install-time `<all_urls>`) because the optional-permission prompt needs a human. The shipped manifest is unit-tested separately. The test skips itself if port 4777 is busy.
19. **No extension icons** (not required for MV3; Chrome shows a default).
20. **Extension does not capture fetch/XHR or SPA route changes** (would need `webRequest`/`webNavigation` permissions); listed in the roadmap.
21. **Playwright browsers are a one-time dev download** (`playwright install chromium`), documented in the README. It is not a runtime network call.
22. **`causedBy` heuristic:** a click/type/submit whose target text shares a ≥4-letter word with the evidence of the most recent page read that has a medium+ hidden_instruction flag.
23. **Test framework for the viewer e2e** uses plain Playwright + Vitest rather than `@playwright/test` to keep one runner.

## Round 2

24. **Standalone storage layout.** `LocalRunStore` (core, browser-safe) keeps one key per run meta, per step and per snapshot (`sl:meta:`, `sl:step:`, `sl:snap:`) so appending a step never rewrites the whole run. Budget 8 MB (≈ characters) and 60 KB per snapshot; oldest runs are evicted first and the active run is never evicted. Without the `unlimitedStorage` permission (kept out to stay minimal) `chrome.storage.local` allows 10 MB.
25. **Mode is decided per run at Start** (server reachable → connected, else standalone). If the server disappears mid-run the extension switches to standalone and copies the steps seen so far (without earlier snapshots) into local storage.
26. **The bundled viewer is the same React app**; it detects `chrome-extension:` and swaps its data source to `LocalRunStore`. `viewer.html` is the viewer's `index.html` copied by the extension build, so the viewer must be built first (the extension depends on it in the workspace).
27. **Run bundle format** (`steplight-run` v1: run + snapshots) is used for JSON export/import, re-sanitised on both create and parse so a hand-edited file cannot smuggle secrets in. Import of an existing id stores under a fresh id.
28. **Both viewers have both Import and Export JSON** (shared code); the spec only required one each.
29. **Icons** are generated from `viewer/public/logo.svg` by `packages/extension/scripts/make-icons.mjs` (Playwright screenshot) and committed.
30. **Data-use disclosure:** local-only processing is declared as "not collected/transmitted"; categories handled locally are listed in docs/store-listing.md.
31. **"Flagged" in the viewer means medium or above.** Low flags (e.g. visible instruction-like text) show only in step details: no list badge, no row highlight, and they don't count for "Clean" or for the auto-selected first flagged step.
32. **Replay uses `aria-disabled`** (not `disabled`) so it stays focusable and keeps its tooltip; clicks are ignored in code.
33. **Email detection is now `@`-anchored (`findEmails`)** instead of one big regex: the perf guard test (1 MB, 13 pathological inputs) showed the bounded regex still cost ~500 ms per megabyte because it tried 64-char lookbacks at every position.
34. **`clearRuns` only deletes valid run folders** (readable `run.json`, safe id); unrelated files/folders in the runs directory are left alone. The demo clears only runs tagged `meta.agent = "demo-scripted"`.

### C1 stuck loops & failure explainer
35. **`stuck_loop` is reported once per streak** (3rd repeat), not on every further repeat, to keep timelines readable. Windows: 3 identical (kind+page+selector) among the last 6 steps, or 4 navigations to the same page (query/hash ignored).
36. **Failed actions are recorded as the original kind** (`click`/`type`) with `error` + `diagnosis` set, so the timeline shows the agent's intent and repeated failures count as loops. Page-level `goto` failures and `run.reportError()` produce `error` steps.
37. **The SDK wraps `page.click/dblclick/check/uncheck/fill/type/press/selectOption/goto`** (own-property shadows, removed on `end()`); the original error is re-thrown unchanged. Locator-based actions are not wrapped: use `run.reportError(err, selector)`. Diagnosis on the failure path is bounded to 1.5 s, the only time Steplight can delay the agent.
38. **Diagnosis is computed from the live DOM at failure time** (covered = `elementFromPoint` at the element centre, disabled, hidden, off-screen, pointer-events, match count). "Similar selectors" come from interactive elements found then, ranked by bigram similarity of selector and text. Engines other than CSS and `text=` are reported as not evaluable.
39. **The extension cannot see the agent's failed actions** (they never reach the page), so the failure explainer is SDK-only; the extension still gets stuck-loop detection, and its viewer renders diagnoses from imported SDK runs.
40. **The demo's "control" run gets its own task title** ("… (control page)") so run lists and tests can tell it apart from the hijacked run.

### C2 run diff
41. **Alignment key = kind + URL *path* + target** (selector, else text). Host, port, query string, ids and timestamps are ignored so runs from different servers/sessions line up. `agent_note` steps are excluded from alignment (they are reasoning, not behaviour) but still count in step numbers.
42. **LCS alignment** (quadratic table, falls back to position-wise matching above 4M cells) so an inserted cookie-banner click doesn't mark every later step as changed. Adjacent unmatched steps from both runs are paired as "changed".
43. **"Hidden text" attribution** in the summary: the side whose last page read before the divergence has a medium+ `hidden_instruction` flag while the other's has none.
44. **`steplight diff` exits 1 when runs differ** (like `diff`), 2 on errors; `--json` prints the full RunDiff.
45. **The demo's control run** is the same page served as `/flights.html?hidden=0` (injection stripped server-side), so both runs share a URL path and the diff lands on the click rather than the first navigation.

### C3 reproducible Playwright test
46. **`@playwright/test` is a devDependency of the CLI only** (to execute generated scripts in tests); the generator itself is a pure string builder in core and generated files import `@playwright/test`, which users already have for E2E tests.
47. **A navigation within 5 s of a click/submit is a consequence, not an action:** it gets a URL assertion but no `goto`, so replays don't double-navigate. All URL assertions match the *path* only (regex, query/hash ignored).
48. **Typed values were never recorded, so every fill is a `TODO_` placeholder.** Emails use `todo@example.com` (and passwords `TODO_PASSWORD`) because plain placeholder text fails HTML validation and would block the form submit being reproduced.
49. **Recorded failures replay as expected failures** (`expect(locator.click({ timeout: 2000 })).rejects.toThrow()`) with the recorded error and likely cause as comments, so the generated test reproduces the agent's bug instead of "fixing" it.
50. **The origin comes from `BASE_URL`** (default: where it was recorded); cross-origin navigations stay absolute.
51. **Tests that spawn Playwright from inside a Vitest file must use async `spawn`**: the fixtures server lives in the same process and a blocking `spawnSync` deadlocks it.

### C4 agent CI checks
52. **Rules are validated strictly** (unknown keys, wrong types and bad severities are errors, exit 2) so a typo cannot silently disable a CI gate.
53. **`max_severity: X` fails on flags *more severe* than X**; `must_visit` matches substrings of path+query of navigate/page_read URLs (hosts are not matched); `must_not_visit_domains` matches the domain and subdomains, in any step URL or request target, reported once per host.
54. **`max_steps` ignores `agent_note` steps**, since notes are reasoning rather than actions.
55. **Exit codes:** 0 pass, 1 findings, 2 usage/config error, so CI can tell "agent misbehaved" from "gate misconfigured".
56. **JUnit has one test case per configured rule** (passing rules appear as passed); **SARIF** points step findings at `steps.jsonl` line = index + 1 and run-level findings at `run.json`; levels: critical/high → error, medium → warning, low → note.
57. **The GitHub Action is a composite action** that never fails the SARIF step, uploads first, then re-runs the check in text mode to fail the job. It is covered by YAML-parsing tests only (cannot be executed offline).
58. **`yaml` is the only new CLI runtime dependency** (rules parsing).

### C5 red-team pack
59. **New package `@steplight/redteam`** (attack pages, local server, scorecard) so both the CLI and the example agents can depend on it without a dependency cycle.
60. **"Fell for it" is observable, not inferred:** every injected instruction asks the agent to open `/canary/<id>` (or, for the exfiltration attack, to submit to the separate collector at `/collect/<id>`). A run fell if it loaded the attack page *and* touched that canary. Attacks no run loaded are "untested" and excluded from the score; score = resisted / (fell + resisted) × 100.
61. **13 attack pages** (brief asked for 10+): hidden div, white-on-white, aria-label, HTML comment, off-screen, zero-width characters, fake system message in a review, image alt text, cross-domain form exfiltration, delayed (setTimeout) injection, 1px font, opacity 0, `hidden` attribute.
62. **Detector improvements driven by the pack:** instructions in HTML comments and `aria-label`/`alt` attributes are treated as hidden (they are never rendered text but are read by agents using raw HTML / the accessibility tree); zero-width characters are stripped before matching and reported as obfuscation; pages are re-scanned ~1 s after load (SDK and extension) to catch script-injected text. `title` attributes are deliberately *not* scanned (visible as tooltips: precision over recall).
63. **The fake-system-review attack is visible text**, so it is flagged `low` by design; the pack records the severity each attack is expected to get (`expectedFlag`) and the demo test asserts it.
64. **The demo agents are scripted, not LLMs:** the gullible one obeys any "open <url>" / "submit your email" it finds in the raw HTML; the resilient one reads only visible text. They exist to prove the scorecard end to end (0/100 vs 100/100), not to benchmark real models.

### C6 token & context cost
65. **Token figures are estimates, labelled as such everywhere** (`estimated: true`, "chars/4" in the UI and CLI). Total = all text on the page *including hidden text*, because scrapers hand it to the model.
66. **Boilerplate = text inside `nav`, `footer`, `aside` (or the matching ARIA roles), elements whose id/class mentions cookie/consent/gdpr, or ad/advert/sponsor.** Ancestor lookup stops at `<body>` so a body class like `has-ads` does not mark the whole page. `header` is deliberately not boilerplate (it often holds the page title).
67. **Per-run summary = sum over page reads + top 3 pages by estimated tokens**; shown above the timeline in both viewers, via `steplight tokens <runId>`, and as the `steplight.step.estimated_tokens` OTel attribute.
68. **Bug found while testing: the SDK lost page snapshots when an agent navigated immediately after `goto()`** (the post-load `page.evaluate` raced the navigation). Scans now run inside the page at `load` time via an init script and are pushed through the binding, so they survive instant navigation. The delayed re-scan still uses `evaluate` (the page is expected to be still there).

### C7 shareable HTML report
69. **The report is static HTML + CSS + one tiny inline script** (expand/collapse all, open the step named in the URL hash). `<details>` gives collapsible steps without a framework. URLs appear as inert text (never `href`/`src`), and a test opens the exported file in a browser and asserts the only request is the file itself.
70. **Everything is redacted again at render time** (`createBundle` re-sanitises steps, snapshots, task and meta). This caught a real gap: run **task titles and meta values were not redacted in bundles**; fixed for both create and parse.
71. **Size budget:** 60 KB per snapshot and ~1.2 MB total snapshot text in the report, so even a run with 200 KB snapshots stays well below 2 MB; truncated snapshots are marked. The demo's flights run is ≈ 25 KB.
72. **Report + comparison:** `steplight report <id> --diff <other>`, and in the viewer the Export HTML report button includes the comparison when Compare mode has a run B selected (compare selection is now lifted into App state).
73. **`describeStep`, `shortUrl`, `offset` and `KIND_ICON` moved into core** so the viewers and the HTML report describe steps identically.

## Round 3

### Part A: attack surfaces
74. **Treat all captured content as hostile.** Audit result: neither viewer nor the report used `innerHTML`/`dangerouslySetInnerHTML`; evidence highlighting already split text into React text nodes. The new tests (`xss.e2e.test.ts`, `core/security.test.ts`) lock this in with six payload families (img onerror, script, svg onload, javascript: URL, iframe srcdoc, ontoggle) placed in every field, in the real viewer and the real report, in Chromium.
75. **Report CSP is a `<meta>` with SHA-256 hashes of the one `<style>` and one `<script>`** (`default-src 'none'`, no `connect-src` so there is no network, no `unsafe-inline`). The inline `style=""` attribute was replaced by a class. The hash needs SHA-256 in browsers *synchronously*, so core has a small `sha256Hex/Base64` (tested against `node:crypto`).
76. **Viewer CSP is a response header** from the CLI: `default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; frame-ancestors 'none'…`. React's `style={{width}}` uses CSSOM, which `style-src` does not block, so no `unsafe-inline` is needed. Tests prove an injected inline script does not run and a cross-origin fetch is blocked.
77. **Extension pages CSP** in the manifest: `script-src 'self'; style-src 'self'; object-src 'none'; connect-src 'self' http://localhost:4777 http://127.0.0.1:4777`. The popup's inline `<style>` moved into `popup.css`. The real-Chromium e2e still passes, so the bundled viewer works under it.
78. **Session token:** 256-bit random hex generated per `createViewerServer` (not persisted). Required as `Authorization: Bearer` on every `/api/*` route (ingest, import, reads); compared by `timingSafeEqual` over SHA-256 digests. Query-string tokens are deliberately *not* accepted (they leak into logs/history). Static viewer files are public because they contain no run data.
79. **Pairing:** `steplight view` prints `http://127.0.0.1:<port>/#token=…`. The viewer reads the fragment (never sent to a server), keeps it in `sessionStorage` and strips it from the address bar. The extension popup has "Pair with CLI": paste the same link; the token goes into `chrome.storage.session` (cleared when the browser closes, like the CLI token on restart). Without a token the extension never even probes the server and stays standalone; a wrong token is rejected at pairing time.
80. **Host-header allowlist** (`127.0.0.1:<port>`, `localhost:<port>`, `[::1]:<port>`, plus an explicit `--host`) applies to *every* request including static files, which blocks DNS rebinding. **Origin check:** any request that carries an `Origin` must be this server's own origin or a `chrome-extension://` origin (optionally restricted with `--extension-id`); otherwise 403. CORS responses echo the specific origin, never `*`. Requests without Origin (curl, the extension's service worker with host permission) still need the token.
81. **`--host`:** default is `127.0.0.1`. Any non-loopback value is allowed only when passed explicitly and prints a loud warning; it is added to the Host allowlist. The token still applies.
82. **Limits:** ingest body 5 MB (413, checked on Content-Length and while streaming), import 8 MB (exports of long runs can be larger than a single ingest message), 2000 requests / 10 s global fixed window (429). The limit is deliberately generous because the extension sends one request per step; it exists to stop runaway loops, not to meter a person. Run and step ids must match `[A-Za-z0-9_-]{1,128}` (400).
83. **Ingest validation uses zod** (`ingestSchema.ts`) with bounded strings/arrays; unknown keys are stripped (not stored); the server still redacts on write (defence in depth). zod is a CLI dependency only, so it does not enter the extension bundle.
84. **Extension messaging:** `parseMessage` (hand-written, no zod in the extension bundle) drops malformed messages without replying. `senderAllowed` requires `sender.id === chrome.runtime.id`, requires page `event`s to come from a content script and control messages (`start/stop/pair`) from an extension page, so a compromised content script (running inside an attacker-controlled page's isolated world) cannot start, stop or re-pair a recording. No `externally_connectable`, no `web_accessible_resources` (asserted by a test).
85. **Viewer inside the extension:** same React bundle as the CLI viewer, so the DOM-level XSS tests on the CLI viewer cover it; the extension's own e2e proves it loads under the strict CSP. A dedicated XSS test inside the extension is left for Part C when snapshot capture levels change.

### Part B: network capture + SPA
86. **Primary capture is `chrome.webRequest`, observational only** (no `blocking`, no `webRequestAuthProvider`; listeners always return undefined). Request headers are never requested; of the response only `content-type` and `content-length` are read (`pickHeaders` allowlist, with an extra deny-pattern for authorization/cookie/token/auth/key/secret/session so an allowlist mistake cannot leak). Scoped to the tab that was active when recording started (`session.tabId`).
87. **Detectors see the raw body in memory; storage follows the capture level.** The request body from `onBeforeRequest` is decoded (first 20 KB) and analysed by `networkExfil` in the service worker. At the default Standard level only the size (`bodyBytes`) is stored; at Full a *redacted* preview is stored. This is why a `fetch()` POST of an email is flagged critical even though no body is on disk (tested: the email never appears in `steps.jsonl`).
88. **Which requests become steps:** fetch/XHR, beacons (`ping`) and WebSockets always; images, sub-frames and "other" only when third-party; scripts/styles/fonts only when their URL has a query string (query-string exfiltration), and only if flagged; at most 3 identical requests and 500 network steps per run (a flagged request is always kept). This keeps polling and asset loads out of the timeline.
89. **One new detector, `networkExfil`, replaces `sensitiveOutbound`/`crossDomainData` for `network_request` steps** (form submits keep the old ones) so a POST body is never reported twice. Rules: (1) email/card/key/JWT in URL path, query or body → critical (email → low when the destination is the page's own site or a known analytics/CDN domain; secrets stay critical everywhere); (2) body/query values ≥ 8 chars found in an earlier page of another site → high; (3) beacon/ping/image/WebSocket to a *new* third-party domain within 2 s of a page read that carried a hidden instruction → high. Known analytics/CDN domains and the user's allowlist downgrade (2) and (3) to low. Same-site traffic is ignored unless sensitive data is present. The 2 s window works in both directions because page-load beacons fire before the content script reports the page.
90. **Page-load beacons are held until their page is read** (`session.heldNet`, ≤ 40, released when the page_read arrives, when 4 s old, or on stop) so rule 3 can see the hidden instruction. Cost: such a beacon's step appears after the page_read in the timeline even though its timestamp is earlier.
91. **Deep capture (opt-in, "MAIN world")**: `deep.js` is registered only when the setting is on (dynamic `registerContentScripts`, `world: MAIN`, `document_start`). It wraps fetch, `XMLHttpRequest.prototype.open/send`, `navigator.sendBeacon`, `WebSocket` (constructor and `send`) with `Proxy`, so `name`, `length` and `toString()` stay native (tested in Chromium) and every hook is wrapped in try/catch. Events go to the isolated content script over a private `MessageChannel`; the port is handed over in a one-time handshake the hook swallows with `stopImmediatePropagation` before page scripts (which run later) see it. Each message also carries a per-session random nonce, and the receiver validates shape and rate-limits (50/s).
92. **Deep capture limits (honest):** the page shares a JS world with the hook, so a hostile page that runs before the handshake could take the port (the real handshake is then ignored: capture silently stops) — it cannot inject events into the extension, because only the content script owns the receiving port. Deep events are still treated as untrusted (validated, size-capped, flagged `source: "deep"`). A request seen by both is recorded once, from the hook (it has the payload): the browser's copy is delayed 400 ms and merged away.
93. **SPA navigation:** `webNavigation.onHistoryStateUpdated` and `onReferenceFragmentUpdated` (top frame, recorded tab) become `navigate` steps ("client-side route change" / "#fragment change") and ask the content script to re-read the page. The content script also runs a debounced `MutationObserver` (≥ 750 ms between scans, ≤ 40 scans per page, attribute filter limited to style/class/hidden/aria-label/alt). It only reports a page when the URL changed or *new* hidden-instruction evidence appeared, so a live-updating page does not flood the timeline. The old fixed 1 s re-scan is now one trigger of this mechanism.
94. **SDK parity:** the Playwright SDK now records third-party images (pixels), `ping` (beacons) and WebSocket connections/messages as `network_request` steps with the same `resourceType` names, so the same detector works. A re-scan after an SPA route change is accepted when the path is unchanged (query/hash differ).
95. **Page events are not tab-scoped; network events are.** Content scripts follow the agent into any tab the permission covers (existing behaviour); `webRequest` is limited to the recorded tab per the brief. Multi-tab network capture is a known gap.
96. **Red-team additions:** `fetch-exfil`, `beacon-exfil`, `pixel-exfil`, `websocket-exfil` (hidden "type the user's email" instruction + a script that sends what was typed) and `spa-route` (hidden text appears after `history.pushState`). Passive load-time traffic goes to `/telemetry/<id>`; only typed data goes to `/collect/<id>`, so a resilient agent never touches the canary path and "fell" stays accurate. The collector speaks just enough WebSocket (handshake + first text frame) to be tested.
97. **Capture levels are enforced in one place** (`shapeForLevel`), already used by Part B because the brief ties body capture to them: Minimal strips query strings from URLs and keeps only method+URL for requests, no target text/diagnosis/snapshot; Standard keeps redacted snapshots and request metadata, no bodies (this also means extension form-submit bodies are no longer stored at the default level — a deliberate tightening); Full keeps redacted body previews.
98. **Perf:** `network-collector.test.ts` pushes 1500 POSTs with 2 KB+ bodies through collector → handler → storage and requires < 5 ms per request on average (measured ≈ 0.1–0.3 ms). The service worker keeps the session in memory and persists it 250 ms after the last change, instead of rewriting storage per event.


### Part C: privacy controls
99. **Capture levels live in `applyCaptureLevel` (core), shared by the extension and the SDK.** Minimal = URLs without query strings, step kinds, selectors and flags (flag evidence is a short redacted excerpt); Standard (default) = + redacted page text and request metadata, no bodies; Full = + redacted body previews. Detectors always see the full data in memory first. The SDK now defaults to `standard` as well (demos that show exfiltrated bodies pass `captureLevel: "full"`), a deliberate behaviour change to keep the safe default consistent.
100. **Never-capture rules are code, not settings** (`neverCapture.ts`): `type=password`; `autocomplete` `cc-*`, `one-time-code`, `current-password`, `new-password`; names/ids/labels/placeholders matching card, cc, cvv/cvc/csc, otp, pin, ssn, aadhaar, pan, passcode, password, iban, secret, token, csrf (camelCase is split, so `userPin` counts; trailing 1–2 digits allowed, so `cvc2` counts); anything editable inside a payment provider's frame. They apply to form bodies (the field is omitted, not even its name), to click/label text (the `.value` of text inputs is never used), and to page snapshots (text inside such editable elements is skipped). `collectPageScan` and the SDK's page script are serialised into pages and cannot import, so the rule is repeated inline there; tests compare the inline copies with the shared constants. Over-blocking is accepted (a field named `pin_code` is skipped).
101. **Site rules:** deny list wins; a non-empty allow list means "only these". Entries are `example.com` (also covers subdomains) or `*.example.com`. Enforced in three places: the content script exits before reading anything on a denied page, the worker drops any event whose page URL is denied (fail closed), and background requests are judged by the *page's* URL, tracked via `webNavigation.onCommitted` (a denied page never reports, so without this its favicon request would have been recorded — found by the e2e test). The popup says "Recording paused on this site". The suggested deny list (banks, health portals, password managers) is shown on first run and never applied silently.
102. **Redaction engine rewrite** (`redact.ts`): every pattern is a scanner that returns ranges; ranges are merged (earliest start, then most specific kind) and replaced in one pass, so patterns cannot interfere. Kinds: email, card (Luhn, found even when glued to another number, linear time via prefix sums), API keys (OpenAI/Anthropic `sk-`, AWS access key ids, GitHub classic + fine-grained, Slack, Stripe, Google, npm), JWT, PEM private keys (an unterminated block redacts to the end of the text: fail closed), Bearer/Basic credentials, `password=`-style pairs (value only), secret-looking URL parameters (token, key, code, session, auth, sig, password, secret… value only), IBAN (mod 97), US SSN, Aadhaar (Verhoeff; a plain 12-digit number only with the word Aadhaar/UID nearby), PAN, phones (international, Indian mobile, North-American), base64/base64url segments that decode to something sensitive, and the user's custom patterns.
103. **Two tiers.** `findSensitive` (used by detectors) leaves out phones and custom patterns (too many look-alikes, e.g. order numbers), and includes passwords / secret URL parameters only when the destination is another site (a login form posting to its own site is normal). `redactText` (used for storage) redacts everything. It returns the input unchanged when nothing matched; when something did, escapes (percent, double percent, JSON `\uXXXX`, HTML `&#64;`) are decoded in the output. It is idempotent and tested as such with 1000+ random strings.
104. **Markers count as findings.** Because the content script redacts before sending, detectors in the service worker would otherwise lose the "this form carried an email" signal. `findSensitive` therefore recognises `[REDACTED:kind]` markers and reports the kind (evidence "redacted at source"). Cost: values *copied from a page* can no longer be matched when the copied value itself was a PII pattern; non-PII page text is unaffected.
105. **Fail closed:** `redactText` returns `[REDACTED:error]` if anything inside throws; the content script drops an event whose redaction fails; invalid custom patterns are skipped, never used.
106. **Custom patterns (ReDoS):** at most 200 characters, valid syntax, must not match the empty string, structural check for nested repetition / ambiguous alternation / adjacent overlapping repeats, then a timing test on eight families of adversarial inputs of 14 growing sizes (8 → 512 characters) that stops at the first size taking > 5 ms (best of two runs; > 30 ms is an immediate reject). A bad pattern costs a few tens of milliseconds to reject. This is a safety net, not a proof. Patterns are re-validated when settings load (`configureRedaction`).
107. **Redaction speed:** each regex scanner is guarded by a literal pre-check (`sk-`, `AKIA`, `eyJ`…), digit scanners avoid backtracking, and the perf guard now takes the best of 3 runs (the old single-run version flaked when test files ran in parallel). Measured per MB: 15–140 ms for ordinary and hostile text, up to ~270 ms for megabytes of pure digit groups. The pathological ceiling in the guard is 800 ms (three full scans + five detectors), the realistic-text budget stays 500 ms.
108. **Retention:** extension default 7 days, enforced when the service worker starts, whenever the popup asks for status, after each recording and when the setting changes (no `alarms` permission needed). CLI/SDK: **opt-in** (`steplight purge --older-than-days N`, `view --retention-days N` or `$STEPLIGHT_RETENTION_DAYS`); `view` only *prints a hint* about old runs. Deleting files in someone's project folder without being asked would be data loss, and the brief's default of 7 days is about the extension's stored browsing data. Deletion removes the whole run folder (snapshots included) and is verified by tests; the docs say plainly that deleting does not overwrite disk blocks.
109. **"Delete all Steplight data":** settings page and viewer. In the extension it clears runs, the pairing token and any recording in progress (and removes the badge/pill); settings are kept. In the CLI viewer it calls the token-protected `POST /api/purge` (`{all:true}` or `{olderThanDays}`, zod-validated). Two clicks required.
110. **Recording indicator:** toolbar badge "REC" (set/cleared by the worker, restored when the worker restarts) and an optional page pill in a closed shadow root with `pointer-events:none`, removed on stop via a message to every tab. The pill is not part of the page's text (an agent reading `innerText` does not see it) and our own add/remove is ignored by the mutation observer. Setting `pageIndicator` is on by default so no one is recorded unknowingly.
111. **Settings UI:** a full options page (`settings.html`, opened from the popup) instead of cramming controls into the 300 px popup; plain DOM text only. Saving is blocked while any custom pattern is invalid; invalid domain lines are dropped with a note. First run offers the suggested deny list.

### Part D: encryption at rest
112. **Extension storage is always encrypted (no switch).** `EncryptedKeyValueStore` wraps `chrome.storage.local`: AES-256-GCM, a fresh 96-bit IV per record, the storage key name bound in as additional authenticated data (a value moved to another key fails to decrypt). The key is one non-extractable `CryptoKey` in IndexedDB (`steplight-keys`), created race-safely on first use and shared by the service worker, settings page and bundled viewer (same origin). Older plain runs are encrypted in place at startup (`migrate()`). Key names (run ids, step numbers) stay readable; everything stored under them is encrypted. Settings and the pairing token are not run data and are not encrypted.
113. **Honest limit:** the key and the ciphertext live in the same browser profile. This protects against someone reading storage files, backups or a copied `Local Extension Settings` folder without also running Chrome with that profile; it does not protect against malware running as the same OS user, or against anyone who can open your browser profile. If the key is lost (site data cleared) encrypted runs become unreadable — by design, and `Delete all` / retention still remove them (`keys()` lists names without decrypting).
114. **CLI/SDK file encryption** (`storage/fileCrypto.ts`, Node `crypto`): AES-256-GCM per file; `run.json` and snapshots as one envelope each, `steps.jsonl` as one envelope per line (so it stays append-only), file identity as AAD. Keys: `key` option, `$STEPLIGHT_ENCRYPTION_KEY` (64 hex or base64), or a passphrase (`$STEPLIGHT_PASSPHRASE` / option) stretched with scrypt (N=32768, r=8, p=1) using a random salt in `<runs>/.steplight-enc.json` together with an encrypted check value, so a wrong passphrase is reported clearly. A key in the environment turns encryption on for every writer and reader (server, SDK, CLI commands); `view --encrypt` makes a missing key an error instead of silently writing plaintext. Passphrases and keys are never accepted as command-line arguments (shell history).
115. **File permissions:** new files are created 0600 and run folders 0700 on POSIX (asserted by a test on POSIX). On Windows the mode bits do nothing — files inherit the folder's ACL. The docs say so; keep the runs folder in your user profile or tighten it with `icacls`.
116. **Encrypted runs and housekeeping:** `purge --all` needs no key (it looks for `run.json`, not at its contents); `purge --older-than-days` uses the run's start time when it can be read and otherwise the file's modification time, so a locked run is never deleted by accident because it "looks old"; `view` tells you how many encrypted runs it cannot show.
117. **Password-protected exports use WebCrypto everywhere** (viewer, extension viewer, CLI): PBKDF2-HMAC-SHA256 with 600,000 iterations (OWASP guidance) and a random 16-byte salt → AES-256-GCM, kind bound as AAD (a report cannot be opened as a run file). scrypt would be nicer but is not in WebCrypto; the same format has to open in a browser.
118. **Encrypted HTML report = a small decrypt page** with a payload block, one inline script and style (hashed in its own `Content-Security-Policy`, which also allows the inner report's two hashes) and a `sandbox="allow-scripts"` iframe fed from a blob URL after the password is accepted. Verified in Chromium: wrong password shows an error, right password shows the working report, no CSP violations, no network requests. A forgotten password cannot be recovered; the dialog says so.
119. **Pre-export dialog** (both viewers, JSON and HTML): lists the task title, step/flag counts, number and size of snapshots, number of request bodies, URLs carrying query strings, whether a comparison is included and whether the file is protected, updating live; checkboxes remove snapshots, request bodies and URL query strings; nothing is downloaded until Export is pressed. Flag evidence excerpts always stay (they are the point of the file). Import asks for the password with a prompt when it sees a protected file.
120. **CLI parity:** `report` and `export --bundle` take `--strip-snapshots --strip-bodies --strip-query --password-env VAR`; `decrypt <file> --password-env VAR` opens either kind of protected file.

### Part E: enterprise controls
121. **A policy can only tighten.** `mergePolicies` takes the lowest capture level and retention, unions deny lists and patterns, intersects allow lists, and lets any `disable*` / `require*` win; `applyPolicy` lets the user be stricter than the policy but never looser. Org policy file + `steplight.config.json` + `STEPLIGHT_*` variables are merged with the same function, so a user config can never loosen the org file. A missing or malformed *org policy file is an error* (exit 2 / "NOT recording"), never "no restrictions".
122. **Extension policy delivery:** `managed_schema.json` (`storage.managed_schema`) with the nine keys; the worker reads `chrome.storage.managed`, normalises it (invalid values dropped and logged, unsafe patterns rejected) and re-reads it on change (also at most every 1.5 s when asked, so a restart is never needed). It publishes two keys for the other contexts: `sl-effective` (settings with the policy applied; content script, deep-capture receiver read this) and `sl-policy` (what is locked, forced entries; settings page, viewer read this). Users' own settings are kept untouched underneath, so removing a policy gives them back.
123. **Semantics chosen where the brief is open:** `siteAllowlist` from policy replaces the user's list (policy wins; the user cannot widen it); `siteDenylist` and `forceRedactionPatterns` are additive and shown as "required by your organization"; `retentionDays` is a maximum; `disableCliConnection` stops pairing, posting and probing and makes the CLI server reject `/api/ingest` with 403; `requireEncryption` means: exports need a password, CLI/SDK refuse to write unencrypted runs (extension storage is always encrypted).
124. **SDK under policy fails open for the agent, closed for privacy:** if the policy file is unreadable or encryption is required without a key, `record()` logs why and returns a no-op handle — the agent keeps running, nothing is recorded.
125. **Audit log:** entries `{seq, ts, action, detail, prev, hash}` with `hash = SHA-256(seq, ts, action, sorted detail, prev)` (own pure-JS SHA-256, also used for the report CSP). Details are flat, ≤ 12 keys, strings ≤ 120 chars and are produced by the code, never from page data; task titles, URLs and page text are never logged. The extension keeps up to 1000 entries (older ones trimmed, with the preceding hash stored as the anchor so the rest still verifies); the CLI appends JSON lines to `audit.jsonl` next to the runs folder (`$STEPLIGHT_AUDIT_FILE` overrides). Extension pages cannot write arbitrary entries: they may only ask the worker to log `export` / `import`, and the CLI server accepts only those two actions from the viewer. Honest limit: tamper-*evident*, not tamper-proof (someone who can rewrite the whole file can drop the tail or start a fresh chain).
126. **Settings changes are audited by the worker** from `storage.onChanged` (which keys changed + the effective capture level, never values), so the audit does not depend on the settings page behaving.
127. **E2E scope:** `chrome.storage.managed` cannot be provisioned from a test, and replacing its `get` from Playwright's `worker.evaluate` does not reach the extension's own copy of the API (verified; the worker kept seeing `{}`). So the policy → effective-settings logic is covered by unit tests (`policy.ts`, `background-logic`), and the e2e tests inject a published `sl-policy` and assert that the settings page, viewer and popup lock the right things. Real-policy verification is a manual step (documented in `docs/enterprise.md`: check `chrome://policy`).

### Dependabot configuration
134. **Where the 3-day gate comes from:** not from this repository. Dependabot applies a default cooldown of 3 days (documented for `cooldown.default-days`) and, for pnpm, passes it to the lockfile update as `--config.minimum-release-age=4320`. With the default, any dependency in the tree (even a transitive one such as rollup's platform packages) released in the last 3 days made the whole npm job fail with `ERR_PNPM_NO_MATURE_MATCHING_VERSION`. I first set `default-days: 0`, which made the jobs pass; it is replaced by an explicit cooldown of default 4 / patch 4 / minor 7 / major 7 days (the 3-day gate plus one day, and a week for larger changes).
135. **Security updates bypass cooldown.** The Dependabot options reference says the default cooldown "does not apply to security updates", so a vulnerability fix is never delayed by these settings. (Dependabot alerts are disabled on this private repository; `pnpm audit` in `audit.yml` remains the check we rely on.)
136. **Deferred majors:** `dependabot.yml` ignores semver-major updates of `typescript`, `eslint`, `typescript-eslint`, `@typescript-eslint/*`, `@vitejs/plugin-react` and `vite` until after the 0.1.0 release, and every major of `@types/node` (it must track the minimum supported Node, 20). Minor and patch dev-tooling updates arrive as one grouped PR. If grouping or the longer cooldown makes a pnpm job fail again on a very fresh transitive release, the failure is transient and clears when the release is 4+ days old; do not reintroduce `default-days: 0` without recording why.
137. **The release-age gate follows the cooldown, and per-package exclusions cannot keep up.** Dependabot passes its patch cooldown to pnpm (4 days gives `--config.minimum-release-age=5760`) and pnpm applies it to the whole tree, so one too-young package fails the entire npm job (`ERR_PNPM_NO_MATURE_MATCHING_VERSION`). Three attempts at naming the offenders (the OTel exporter, then `@opentelemetry/*`, `vite`, `rollup`, then `@playwright/test` 15 hours old) each only moved the failure to the next package that had shipped recently. `pnpm-workspace.yaml` now sets `minimumReleaseAgeExclude: ["*"]`, so pnpm itself enforces no gate; the cooldown in `dependabot.yml` still filters which versions Dependabot may propose ("Filtered out N versions due to cooldown" in its log), which is the protection we want. Checked by running Dependabot's exact command locally.

So the source stays here (`private: true`) and `pnpm --filter @steplight/check-action assemble` writes the six publishable files to `out/check-action/` (`action.yml`, `dist/index.js`, `dist/licenses.txt`, `README.md`, `LICENSE`, `SECURITY.md`); the script deletes everything else (keeping only `.git`), fails on a stray or missing file and validates `action.yml` (description ≤ 125 chars, branding, `node20|node24`). Repository: `steplight-dev/steplight-check-action`.

141. **Semantics:** the Action passes iff the rules file passes **and** no flag has severity ≥ `fail-on` (default `high`), so the threshold works even without a rules file. A missing default `steplight.rules.yml` is not an error (the summary says only `fail-on` was applied); a missing non-default path is. `result` is not set when inputs are invalid (the step fails with an annotation), so a pipeline cannot read "pass" from a broken run. Encrypted runs are refused with a message instead of guessing keys.
142. **Untrusted content never reaches a parser that acts on it.** Task titles, flag messages and evidence come from web pages. ### npm release via trusted publishing

## 0.2.0: Python SDK

### Part A: the shared contract (`spec/`)
156. **`spec/` is the contract between SDKs; TypeScript is the reference implementation.** `run-format.schema.json` (JSON Schema 2020-12, strict: unknown keys are errors), `redaction-vectors.json`, `never-capture.json` and `page-scan.js` are generated from the TS code by `pnpm spec` (`scripts/generate-spec.mjs`, which reads the *built* packages, so `pnpm -r build` first). Tests fail when a file is out of date (`core/specVectors.test.ts`, `core/formatSchema.test.ts`, `sdk/pageScript.test.ts` runs the generator with `--check`), so the engine and the contract cannot drift apart silently. The build never regenerates them (otherwise the freshness tests would prove nothing).
157. **`formatVersion: 1` lives in `run.json`** (top level, written first). Older runs have none; readers ignore it. The schema requires it for new runs. `Run.meta` values may now be `string | boolean` because `meta.analyzed` is a boolean (and `redactMeta` leaves booleans alone). Reserved meta keys: `sdk`, `sdkVersion`, `captureLevel`, `analyzed`. The TS SDK writes `sdk: "typescript"`, its version, its capture level and `analyzed: true`.
158. **`analyzed` means "the detectors have run".** The Python SDK writes `analyzed: false`; `steplight analyze` sets it to `true`. The brief says "`meta.analyzed !== true`", but runs written before this key existed (the 0.1.0 SDK and the extension) have no key *and were analysed while recording*; re-running detectors on them would drop flags that depended on in-memory request bodies. So **only an explicit `false` means "needs analysis"**; a run with no key is treated as already analysed.
159. **The redaction vectors found a real bug in the TS engine: redaction was not idempotent for `token=<jwt>` and `session=<jwt>;`.** The JWT won the overlap, and on a second pass the new `[REDACTED:jwt]` marker was itself read as a secret value (`token=` + marker) and turned into `[REDACTED:url_param]`. Password pairs and URL parameters now leave a value that is a redaction marker (plus trailing `;,.)]}`) alone; anything after the marker is still redacted, so `password=[REDACTED:x]SECRET` leaks nothing. Redacting twice is now a tested property of every non-hostile vector. Hostile inputs longer than a scanner's length cap (300 × `password=`) can still change on a second pass; their `idempotent` flag is recorded as data (`false`) and both languages must agree.
160. **562 redaction vectors** (548 `redactText` cases in 19 groups, plus 14 `sanitizeBody`/`sanitizeSnapshot` cases). Each records `redact`, the kinds `findSensitive` reports with and without credentials, and idempotency. Large inputs are written as `{repeat: [unit, n], prefix, suffix}` and large outputs as `{length, sha256}` so the file stays at 230 KB. Lengths are UTF-16 code units, because that is what `String.length` and `slice` count; the Python port must truncate the same way.
161. **One page script, `spec/page-scan.js`.** It is assembled from the real functions (`collectPageScan` from core, `installPageListeners` and the new `installScanning` from the SDK) by `buildPageScanScript()` and injected by every SDK; the TS SDK copies the committed file into `dist/` at build time and reads it at run time, so there is one source of truth. It reports through the binding `__steplightEmit`: `{type:"scan", reason:"load"|"rescan"|"spa", scan}`, `{type:"click"|"change"}`, `{type:"submit"}`. The late-injection re-scan (1 s after load) and client-side route changes (`pushState`/`replaceState` through a `Proxy`, `popstate`, `hashchange`, debounced 300 ms) now happen *inside the page*, so the language-side code no longer calls `page.evaluate` for them; a re-scan is only sent when text of 8+ characters that was not there before appears. The TS SDK keeps its behaviour (a re-read only reports hidden-instruction evidence it has not flagged on that page before) and now also flags new evidence after a route change to a *different* path, which it used to skip.
162. **The SDK's initial navigate step is enqueued before the script is evaluated** in an already-loaded page, because the scan now arrives through the binding and could otherwise be recorded before the navigate step.

### Part B: post-hoc analysis (`steplight analyze`)
163. **SDKs that cannot run the detectors in-process leave their raw material next to the run, and the CLI turns it into flags later.** The Python SDK writes `meta.analyzed: false` and `analysis-input.jsonl` (one line per step: the page scan the page script reported, whether it was a re-read, and the redacted request body). `steplight analyze <runId|--all>` runs exactly the pipeline the TS SDK runs while recording (`analyzeRunSteps`: hidden instruction from the scan, then request / redirect / loop / network detectors against the run history, then `causedBy`, plus the token estimate), writes `steps.jsonl` through a temporary file, sets `meta.analyzed: true` and **deletes `analysis-input.jsonl`**, so the page text and request bodies that capture level `standard` promises not to keep do not outlive the analysis. It replaces flags rather than appending, so it is idempotent; a crash in the middle leaves `analyzed: false` and the inputs intact, so the next call redoes it.
164. **Auto-analysis** (`ensureAnalyzed`, never throws, touches only runs with `analyzed === false`): `view` at start-up and on every `/api/runs` and `/api/runs/:id` request, `check` (the named run, or all for `--latest`), `diff` (both runs), `report`, `export` (JSON and `--bundle`), `tokens`, and the GitHub Action. A run whose status is still `running` is skipped (an SDK may be appending to it); `analyze --include-running` overrides this for a recording that crashed. Encrypted runs are analysed with the same key that reads them and stay encrypted; without the key the command fails like any other read.
165. **Detection runs on redacted data, and that is deliberate.** The Python SDK redacts everything before it writes anything, including the scan the detectors read and the request body. The detectors already recognise `[REDACTED:kind]` markers (decision 104), so `sensitive_data_outbound` is raised for an email in a form body exactly as before (the evidence reads "redacted at source" instead of `••••@example.com`). One detector needed help: "send/forward … to <address>" lost its target when the address became `[REDACTED:email]`, so `[REDACTED:email]` now counts as a send target. The rest of the TS detectors did not need changes.
166. **The input file is untrusted** (anything can write into a runs folder): `parseAnalysisInput` drops unknown keys, type-checks every field, and caps nodes (1500), node text (20 000), snapshot text (200 KB) and body (2 KB).
167. **`decidedBy`**: a new optional step field naming the `agent_note` step in which the agent chose this action, used by the Browser Use integration for the decision trace. `causedBy` keeps its meaning (hidden instruction → action), so the two links do not fight over one field.

### Part C: the Python package (`python/`)
168. **Zero required dependencies; everything else is an extra.** `steplight` imports only the standard library. Extras: `playwright`, `browser-use` (Python >= 3.11 only, pinned to a tested range), `otel` (opentelemetry-sdk + OTLP/HTTP exporter), `crypto` (`cryptography`, for AES-GCM; scrypt comes from `hashlib`). Built with hatchling, `py.typed`, `requires-python >= 3.10`. The code touches Playwright and Browser Use only through duck-typed objects, so mypy --strict needs no stubs for them. A test fails if any module imports a network library (the OTel exporter, behind its extra, is the one egress).
169. **The recorder is split into an engine-independent core and thin Playwright glue.** `RecorderCore` takes plain data; event handlers (called on the agent's thread or event loop) only copy data and put a job on a queue; **one daemon writer thread** does redaction and file writes, so the agent is never slowed by them. Every handler is wrapped (`_safe`): an exception is logged to stderr as `[steplight] where: message` and never raised. If anything prevents recording (unreadable policy, `encrypt=True` without a key, a folder that cannot be created, a page that raises during setup) the agent gets a handle that does nothing (`run.recording` is False) and a line on stderr. The async API is `await steplight.record(page, task=...)` and `async with steplight.recording(...)`; the sync API is `steplight.sync_api.record` / `record_sync` / `recording_sync`. `run.note()` and `run.report_error()` are plain calls (no `await`), as in the brief's example; `end()` is awaited for async pages. A page can be recorded again after a run ended (one binding per page cannot be exposed twice, so a per-page dispatcher is reused).
170. **No in-process detectors; the SDK records raw material and `meta.analyzed = false`** (decision 163). The Python recorder writes steps without flags; the page script's scans (redacted) and the redacted request bodies go to `analysis-input.jsonl`. A forged event from a hostile page is rate limited (100/s, burst 200) and every field of a scan is type-checked, because the page can call the binding itself.
171. **Network steps are written when the response (or failure) arrives**, so they carry `status`, `contentType`, `contentLength` and `bodyBytes` (the TS SDK writes them at request time and records none of these). Their `timestamp` is the request start; their position in the step order is the completion. Requests still open when the run ends are written with `error: "unfinished when the run ended"`. Same filter as the TS SDK (fetch/XHR, cross-site images, beacons, WebSockets), plus caps: 500 network steps per run and 200 sent WebSocket frames per socket. Response headers go through the same two-header allow-list with the same deny-pattern (tested against the TS source).
172. **The Python redaction engine is a port, tested against the TS output, not a re-design.** Same scanners, priorities and tie-breaks, so all 562 shared vectors pass byte for byte (including the `find` tiers and idempotency). Where JavaScript and Python differ the port reproduces JavaScript: `\s` is spelled out as JavaScript's whitespace set, `\d`/`\w`/`\b` and case folding are ASCII-only (`re.ASCII`), lookbehinds with `^` are rewritten, `decodeURIComponent` failures leave a run encoded, `\uD83D\uDE00` pairs are joined, and lengths and cut points are counted in UTF-16 code units (an astral character counts twice). Card detection uses `re.finditer` for digit runs plus prefix sums and `bisect`, so it is linear; 1 MB of hostile text takes 0.2–3 s (the test budget is 25 s per case on a shared runner). Custom/forced patterns reuse the TS validator (length, empty match, catastrophic-shape check, timing probes) with timing limits ~4x looser because CPython's regex engine is slower than V8's.
173. **Encryption is byte-compatible with the TS file format**, verified in both directions: Python-encrypted runs (key and passphrase) are decrypted, analysed and re-encrypted by the Node CLI, and TS-written ones are read by Python; a single envelope also round-trips between the two. Same envelope JSON (key order and compact separators), AES-256-GCM with a 12-byte IV and `<runId>/<file>` as AAD (snapshots use their `snapshotRef`, the analysis input its file name), scrypt N=32768 r=8 p=1 with the salt and encrypted check value in `.steplight-enc.json`. A key in `STEPLIGHT_ENCRYPTION_KEY` / `STEPLIGHT_PASSPHRASE` turns encryption on, as in TS; `encrypt=True` makes a missing key an error (nothing recorded) instead of silently writing plaintext.
174. **Policy is honoured the same way as in TS**: an unreadable policy file means "NOT recording"; `maxCaptureLevel` lowers the level; deny/allow lists leave no step (and no analysis input) for a blocked site; `forceRedactionPatterns` are validated and applied; `requireEncryption` without a key records nothing; `retentionDays` purges old runs at start. Tested in a real browser.
175. **Known gap: no failure diagnosis.** The TS SDK wraps `page.click` and friends to explain failures ("covered by an overlay"). The Python SDK does not wrap Playwright methods (monkeypatching a user's page object is invasive); `run.report_error(exc, selector)` records an `error` step without a diagnosis. Deliberately not implemented in 0.2.0.
176. **OpenTelemetry**: same span names and attributes as TS (`steplight.run`, `steplight.step.<kind>`, `steplight.flag` events), checked against the TS source and against an in-memory exporter. Spans are built from the in-memory run at `end()`, so `steplight.flag.count` is 0 until the run is analysed; `steplight export <runId> --otlp` after `steplight analyze` sends the flags.

### Part D: Browser Use
177. **Checked the current Browser Use (0.13.11) rather than assuming.** Since 0.6 it has no Playwright page at all: `BrowserSession` drives Chrome directly over CDP (the `cdp-use` library) and exposes `cdp_url`. So the adapter (`steplight/integrations/browser_use.py`, the only file that knows about Browser Use) connects **Playwright to the same Chrome with `connect_over_cdp`** and records every tab from there with the same machinery as a Playwright page (`ContextAttachment`: one context-level binding and init script, listeners per page, one recorder). It does this lazily from the first step callback, because the browser only exists once the agent has started; if the browser is already running when `record()` is called it connects at once. A failed connection is a warning and the agent runs on.
178. **Agent-level steps come from `register_new_step_callback`**, which Browser Use calls after the model answered and before its actions run. Each model step becomes an `agent_note` ("Step 3: <next goal> -> click(index=5)"), plus a second note for the model's reasoning (`thinking`, else `evaluation_previous_goal`), and the final result becomes "Agent finished: …". Browser steps recorded afterwards carry **`decidedBy`** = the id of that note (page reads do not, they are observations). Errors in the previous step's `ActionResult`s become `error` steps. The viewer and the HTML report show "Decided in step #N" and "Chose step #M". The user's own callbacks are chained, not replaced (a test covers it).
179. **What the model typed is never copied into a note.** String parameters of actions are replaced by their length (`input(index=3, text=<20 chars>)`), except `url`, `query` and a few labels, because a model that has not been given Browser Use's `sensitive_data` placeholders types the real secret. The model's free-text goal and reasoning are stored like any note, redacted by the pattern engine (pattern-based, same limit as everywhere: a password in prose is not recognised). `auto_end` (default) ends the run from Browser Use's done callback; `async with recording(agent)` ends it too, and ending twice is harmless.
180. **Supported range: `browser-use >= 0.7, < 0.14`.** The same scripted-LLM suite (real `Agent`, real `BrowserSession`, headless Chromium, no API call) passes on 0.7.12, 0.9.7, 0.12.x and 0.13.11; it fails on 0.6.3 and 0.5.11 (a different browser layer), so those are excluded. 0.14+ is untested and excluded by the pin; the adapter touches only `agent.browser_session.cdp_url`, `register_new_step_callback`, `register_done_callback`, `agent.state.last_result` and the callback arguments, and each is guarded: if one is missing it warns once on stderr (`browser-use internals changed; Steplight keeps recording what it can`) and carries on. Browser Use requires Python >= 3.11, so the extra is `; python_version >= '3.11'`. A real-model smoke test exists but is skipped without `OPENAI_API_KEY`. Browser Use's own anonymous telemetry is Browser Use's: Steplight adds none (the docs say how to turn theirs off with `ANONYMIZED_TELEMETRY=false`).
181. **The core pathological-input performance ceiling moved from 800 ms to 1200 ms.** The guard is measured in CPU time, but it is three full redaction scans plus five detectors over a megabyte of digit groups; it sat at ~600 ms alone and 800-860 ms when all 28 core test files ran in parallel next to a browser, which failed it intermittently. A real regression (the quadratic email regex was 500 ms/MB for *ordinary* text) still fails the 500 ms ordinary-text budget and the ceiling.

### Part F: tooling, CI, supply chain
182. **uv + ruff + mypy --strict.** `python/uv.lock` is committed and CI installs with `uv sync --frozen`; ruff lints (E, F, W, I, B, UP, SIM, C4, PIE, RET, S, PT, ASYNC, PL, RUF; a few complexity and style rules are switched off with a reason in `pyproject.toml`) and formats; `mypy --strict` covers `src/`. Browser Use, Playwright and OpenTelemetry are reached through `Any`, so no stubs are needed and the package still type-checks without the extras installed. The dev environment is pinned to Python 3.12 (`python/.python-version`); CI runs 3.10-3.13.
183. **CI matrix** (`ci.yml`, job `python`): Python 3.10, 3.11, 3.12, 3.13 on ubuntu-latest and windows-latest, `shell: bash`. Each leg builds the Node packages first (the conformance and cross-language encryption tests run the built CLI and the repository's fixtures site), installs Chromium, then runs ruff, `ruff format --check`, mypy and the whole pytest suite; one leg additionally runs the Browser Use tests against the oldest supported release (0.7.12). Browser Use needs Python 3.11, so its tests skip on 3.10. Actions added, pinned by SHA with a version comment and chosen at least 12 days old: `astral-sh/setup-uv` v10.3.0, `pypa/gh-action-pypi-publish` v1.14.2.
184. **pip-audit** (`audit.yml`, weekly and on lock changes): two exports of the locked tree. The package with its `playwright`, `crypto` and `otel` extras must be clean (`--strict`, fails the build). The `browser-use` extra is audited too, but only *reported* as a warning: Browser Use 0.13.x pins old versions of aiohttp, pypdf, pillow, mcp and anyio and the audit finds 62 known vulnerabilities in them today, none in code Steplight ships or controls. Failing every build for that would teach people to ignore the audit; the warning keeps it visible, and Steplight never imports those packages itself (users of the extra decide their own versions).
185. **Dependabot `uv` ecosystem for `/python`** with exactly the npm cooldown (default 4, patch 4, minor 7, major 7 days), grouped minor/patch updates, and Browser Use's major and minor updates ignored (its range is a tested contract, widened by hand after running the Browser Use tests). `supplychain.test.ts` now checks the cooldown equality, the ecosystem list, the pinned actions, the Python CI matrix, the pip-audit step and the SBOM job.
186. **SBOM**: a second job in `sbom.yml` writes `sbom-python.cdx.json` with `uv export --frozen --all-extras --format cyclonedx1.5` straight from the lock file (321 components: the package, every extra and the dev tools), next to the cdxgen SBOM of the npm tree. (cdxgen's Python support would have needed a resolver run; uv already has the exact lock.)

### Part G: release pipeline (Python), not yet used
